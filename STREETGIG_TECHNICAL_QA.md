## Q1. Explain the Dual-Vector Profiling system. Why do workers have two separate embeddings?

**Answer:**

Every StreetGig worker maintains **two independent 768-dimensional vectors** generated by `gemini-embedding-001`:

1. **Master Profile Vector (Static)** — Encodes what the worker **can do**. Generated once during registration from their category, experience, and self-description. Updated only when the worker edits their profile.

2. **Skill Gap Vector (Dynamic)** — Encodes what the worker **needs to learn**. Generated after every completed job from the employer's feedback. Updated with each new job completion.

**Why two vectors instead of one?**

If you merge strengths and weaknesses into a single vector, they cancel each other out in the embedding space. Consider a plumber who is excellent at pipe fitting but terrible at customer communication:

- **Single vector approach:** The embedding averages the semantics of "expert pipe fitting" and "poor communication" → the resulting vector is mediocre at representing both, and cosine similarity against a job requiring pipe fitting returns a lower score than it should.

- **Dual vector approach:**
  - Master vector: strongly aligned with "plumbing", "pipe fitting", "repair"
  - Gap vector: strongly aligned with "communication skills", "customer interaction"

**How each vector is used:**

| Vector | Used For | Endpoint |
|---|---|---|
| Master Profile | Job recommendations (matching what workers CAN do to job requirements) | `/recommend-workers` |
| Master Profile | RAG scheme matching — "Upgradation" tab (schemes that enhance existing skills) | `/learning-schemes?type=upgradation` |
| Skill Gap | RAG scheme matching — "Improvement" tab (schemes that fix weaknesses) | `/learning-schemes?type=improvement` |

This means a worker sees two categories of government schemes:
- **Upgradation:** "You're already a skilled plumber — here's an advanced certification"
- **Improvement:** "Your employers noted weak communication — here's a customer service workshop"

## Q2. Walk through the G-RAG (Graph Retrieval-Augmented Generation) pipeline. Why is it better than standard vector search?

**Answer:**

Standard RAG retrieves candidates by computing cosine similarity between a job embedding and all worker embeddings. G-RAG augments this with a **multi-hop graph traversal** over a skill ontology stored in MongoDB.

### Phase 1: Graph Retrieval

When a job is posted, Gemini 2.0 Flash extracts required skills from the job description. Then three parallel retrievals happen:

```
Job: "Need experienced carpenter for furniture assembly"
     │
     ├── Hop 0: Exact Skill Match
     │   Query: graph_edges where type="has_skill" AND skill="carpentry"
     │   Returns: Workers who explicitly list "carpentry"
     │
     ├── Hop 1: Adjacent Skill Match
     │   Query: graph_edges where type="skill_adjacency" AND source="carpentry"
     │   Discovers: "woodworking", "furniture_repair" are adjacent skills
     │   Query: Workers with those adjacent skills
     │   Returns: Workers who don't list "carpentry" but have related skills
     │
     └── Hop 2: Repeat-Hire Boost
         Query: graph_edges where type="completed_for" AND employer=current_employer
         Returns: Workers who successfully completed past jobs for THIS employer
```

**Why Hop 1 matters:** A worker who listed "woodworking" but not "carpentry" would score 0 in a pure keyword match and might score low in vector similarity. Graph adjacency surfaces them because the skill ontology knows these skills are related.

### Phase 2: Composite Scoring

All candidates from all hops are scored:

```
final_score = (0.4 × vector_similarity
             + 0.3 × graph_path_score
             + 0.2 × reputation_score
             + 0.1 × recency_score) × safety_multiplier
```

| Signal | Weight | Details |
|---|---|---|
| **Vector Similarity** | 40% | Cosine similarity between worker's master embedding and job embedding |
| **Graph Path Score** | 30% | Hop-0 = 1.0, Hop-1 = 0.7, Hop-2 = varies based on past rating |
| **Reputation** | 20% | Average star rating from past employers. Cold-start workers inherit the category average |
| **Recency** | 10% | Exponential decay: `e^(−days_since_last_activity / 30)`. Active workers score higher |

**Safety Multiplier:** If the Safety Agent has flagged a worker (e.g., harassment report), their `safety_multiplier` drops below 1.0, reducing their visibility in results without outright banning them.

### Phase 3: LLM Re-Ranking

The top-N candidates are sent to Gemini 2.0 Flash (Context Reranker) which:
1. Re-evaluates each candidate against the original job description
2. Generates a **natural language match explanation** for each (e.g., "Strong match: 4 years carpentry experience, 4.8 rating, completed similar job for you last week")
3. May reorder candidates based on nuanced understanding

**Why G-RAG over pure vector search?**
- Vector search misses workers with related but differently-worded skills
- Graph traversal captures employer-worker relationships (repeat hires)
- The LLM re-ranking adds human-interpretable explanations that build trust
- Composite scoring prevents any single signal from dominating

## Q3. How does the Skill Gap Feedback Loop work? What happens when an employer closes and rates a job?

**Answer:**

The Skill Gap Feedback Loop is StreetGig's continuous learning system. Here's the complete flow:

```
1. Employer closes job + submits rating
   ├── 3 star ratings (Quality, Punctuality, Communication) → 1-5 each
   └── 1 textual comment (free-form feedback)

2. POST /api/streetgig/close-job
   ├── Immediate: Job status → COMPLETED, rating saved
   └── Fire-and-forget: POST /process-skill-gap (to Python agent)

3. skill_gap_agent.py (Gemini 2.0 Flash)
   ├── Input: { ratings: [4, 3, 2], comment: "Good work but late and rude" }
   ├── Agent synthesizes a holistic paragraph:
   │   "Worker demonstrates strong technical carpentry skills (4/5 quality).
   │    However, punctuality is a concern (3/5) and communication was poor
   │    (2/5), with the employer noting rudeness during interaction."
   └── Output: skill_gap_string

4. Embedding generation
   └── skill_gap_string → gemini-embedding-001 → 768-dim vector

5. Worker profile update
   ├── worker.skillGapString = new_gap_string
   ├── worker.skillGapEmbedding = new_768d_vector
   └── These OVERWRITE the previous gap data (most recent feedback wins)

6. RAG Skilling Engine
   └── Next time worker visits Learning Hub:
       └── /learning-schemes?type=improvement
           └── Compares gap_embedding vs gov_schemes embeddings
           └── Returns: "Customer Service Workshop — 89% match"
```

**Key Design Decision — Why overwrite instead of accumulate?**

The gap vector reflects the worker's **current** weaknesses, not historical ones. If a worker fixes their punctuality issue after taking a course, the next employer's feedback should reflect that improvement. Accumulating old gap data would permanently penalize them for past issues.

**Why fire-and-forget?** The employer gets an immediate "Job closed successfully" response (200 OK). The Python agent processes feedback asynchronously because:
- Embedding generation takes 200-500ms
- The employer doesn't need to wait for AI processing
- If the agent fails, the core job-closure logic isn't affected

## Q4. Explain the AI Recommendation Logic. How are jobs ranked for a worker?

**Answer:**

When a worker opens the StreetGig dashboard, the system runs a hybrid ranking algorithm:

```python
# Pseudocode for recommendation logic
candidates = fetch_jobs_in_geohash_neighborhood(worker.geohash6)

for job in candidates:
    job.distance = haversine(worker.location, job.location)
    job.similarity = cosine_similarity(worker.masterEmbedding, job.embedding)

# Sort by distance first
candidates.sort(key=lambda j: j.distance)

# For jobs within 2km of each other, break tie by similarity
for i in range(len(candidates) - 1):
    if abs(candidates[i].distance - candidates[i+1].distance) < 2.0:
        # Sort this cluster by similarity score (descending)
        cluster = get_similar_distance_cluster(candidates, i, threshold=2.0)
        cluster.sort(key=lambda j: j.similarity, reverse=True)
```

**Why distance-first?**

StreetGig targets daily wage workers who primarily travel by foot or public transit. A perfectly matched job 15 km away is useless if the worker can't get there affordably. Distance is the primary constraint.

**Why 2km tie-break threshold?**

Within 2 km, the difference in travel effort is negligible (10-15 minutes by bus or walking). In this radius, **skill match quality** becomes the more important factor. The cosine similarity score (0.0 – 1.0) determines which of two nearby jobs the worker should see first.

**Geohash-based initial filtering:**

Before any scoring, the system only queries jobs within the worker's **9-cell geohash-6 neighborhood** (~3.6 km radius). This is a constant-time Firestore `IN` query, not a full-table scan:

```javascript
const neighbors = ngeohash.neighbors(workerGeohash6);
const allCells = [workerGeohash6, ...Object.values(neighbors)];
// Firestore query: where geohash6 IN allCells AND status == 'OPEN'
```

This O(1) spatial filtering makes the recommendation endpoint fast even with thousands of jobs in the database.

## Q5. How does the RAG Skilling Engine work? What's the difference between Upgradation and Improvement schemes?

**Answer:**

The RAG Skilling Engine is a vector retrieval system that matches workers with government skilling programs. It operates as a standard RAG retriever but with a twist: **it queries against two different vectors per worker.**

### The Two Retrieval Modes

**1. Upgradation (Master Profile Vector):**
```
Worker's master embedding ─── cosine similarity ──→ gov_schemes embeddings
                                                        │
                                                        ▼
                                              "Advanced Welding Certification"
                                              "Plumbing Master Course"
                                              "Electrical Safety Diploma"
```
These schemes enhance what the worker is **already good at**. The master vector captures their current capabilities, so matching against scheme vectors finds programs that build on existing skills.

**2. Improvement (Skill Gap Vector):**
```
Worker's gap embedding ─── cosine similarity ──→ gov_schemes embeddings
                                                      │
                                                      ▼
                                            "Customer Service Workshop"
                                            "Basic English Communication"
                                            "Workplace Punctuality Training"
```
These schemes fix what the worker is **bad at**. The gap vector captures their weaknesses (synthesized from employer feedback), so matching finds programs that directly address those gaps.

### How the `/learning-schemes` Endpoint Works

```javascript
// Simplified flow
async function getLearningSchemes(workerId, type) {
    const worker = await Worker.findById(workerId);
    
    // Select the appropriate vector
    const queryVector = type === 'upgradation' 
        ? worker.masterEmbedding    // What they CAN do
        : worker.skillGapEmbedding; // What they NEED TO learn
    
    // Fetch all government schemes and compute similarity
    const schemes = await GovScheme.find({});
    const results = schemes.map(scheme => ({
        ...scheme,
        matchScore: cosineSimilarity(queryVector, scheme.embedding)
    }));
    
    // Sort by match percentage, return top results
    return results.sort((a, b) => b.matchScore - a.matchScore);
}
```

**Why is this better than keyword matching?**

A worker whose gap is "poor communication, was rude to employer" would never match a scheme titled "Professional Soft Skills Development" via keyword search. But in embedding space, both concepts cluster together because the language model understands they're semantically related.

### Real-World Example:

Worker Ramesh — electrician, 3 years experience:
- **Master vector** encodes: electrical work, wiring, home repair
- After a job, employer rates: Quality 5/5, Punctuality 2/5, Communication 3/5
- **Skill gap string:** "Excellent technical skills but frequently late and needs to improve client interaction"
- **Gap vector** encodes: punctuality, time management, client interaction

**Upgradation tab shows:** "Advanced Electrical Safety Certification (DDU-GKY) — 92% match"
**Improvement tab shows:** "Workplace Discipline & Time Management (Skill India) — 87% match"

## Q6. What is the Safety Agent and how does it integrate with StreetGig?

**Answer:**

The Safety Agent (`safety_agent.py`) is a LangGraph pipeline that audits chat rooms and job descriptions for predatory behavior, harassment, or wage theft signals.

### Architecture

```python
# Simplified LangGraph structure
graph = StateGraph(SafetyState)

graph.add_node("analyze", analyze_content)    # Gemini 2.0 Flash analysis
graph.add_node("classify", classify_severity) # Structured output classification

graph.add_edge("analyze", "classify")
graph.set_entry_point("analyze")
graph.set_finish_point("classify")
```

### Input/Output

**Input:** Chat transcripts, job descriptions, or user reports  
**Output (Structured):**
```json
{
    "summary": "The employer repeatedly demanded personal phone number...",
    "severity": "HIGH",
    "flags": ["personal_info_solicitation", "boundary_violation"],
    "recommended_action": "REVIEW_REQUIRED"
}
```

### Severity Levels

| Level | Trigger | System Response |
|---|---|---|
| **LOW** | Mild unprofessional language | Logged, no action |
| **MEDIUM** | Repeated microaggressions, unreasonable demands | Job flagged for admin review |
| **HIGH** | Personal info solicitation, boundary violations | Worker/employer warned, job moved to REVIEW_REQUIRED |
| **CRITICAL** | Explicit threats, wage theft evidence, exploitation signals | Immediate job suspension, admin notified |

### Integration Points

1. **Job posting:** When a new job is created, the description is sent to the Safety Agent. If flagged, the job isn't visible in recommendations until admin reviews it.

2. **Chat rooms:** Chat messages in StreetGig's real-time Firebase RTDB rooms can be reported by users. The report triggers the Safety Agent with the chat transcript as input.

3. **G-RAG scoring:** The Safety Agent's output feeds into the `safety_multiplier` in the G-RAG composite scoring formula. A worker flagged as HIGH gets `safety_multiplier = 0.5`, halving their visibility in search results without outright banning.

## Q7. Explain the Job Enrichment Pipeline. What happens when an employer posts a job?

**Answer:**

When an employer creates a job, the system performs **background AI enrichment** via a fire-and-forget call to the Python agent:

```
1. Employer submits job via POST /api/streetgig/create-job
   └── Input: { title, description, budget, location, category }

2. Immediate response: 200 OK + jobId
   └── Job saved with status: OPEN

3. Fire-and-forget: POST /process-job (Python FastAPI)
   └── This is a non-blocking Axios call; the employer doesn't wait

4. LangGraph Job Agent (4-node DAG with parallel execution):

   ┌─── Track A (Sequential) ─────────────────────┐
   │                                                │
   │ Node 1: enrich_job_data                       │
   │   └── Gemini 2.0 Flash enhances the description│
   │       with standardized terminology            │
   │                                                │
   │ Node 2: extract_job_skills                     │
   │   └── LLM extracts skill tags from description │
   │       Output: ["carpentry", "furniture", ...]   │
   │                                                │
   └────────────────────────────────────────────────┘
                         ↓
   ┌─── Track B (Parallel after Track A) ──────────┐
   │                                                │
   │ Node 3: generate_embedding                     │
   │   └── Embeds enriched description → 768d vector│
   │                                                │
   │ Node 4: generate_feedback_form (parallel)      │
   │   └── Creates tailored rating questions based  │
   │       on the specific job skills               │
   │       Output: ["Rate carpentry quality", ...]   │
   │                                                │
   └────────────────────────────────────────────────┘

5. Graph Writebacks (MongoDB)
   ├── Update/create skill_nodes for extracted skills
   ├── Update graph_edges: employer → job → skills
   └── Update job document with embedding + enriched data
```

**Why enrichment?** Employers (especially daily wage hirers) often write terse descriptions like "Need guy for fixing cabinet." The enrichment node expands this into standardized language that produces better embeddings: "Requires experienced carpenter for furniture repair and cabinet assembly. Skills needed: carpentry, woodworking, furniture assembly."

**Why tailored feedback forms?** Generic feedback ("Rate 1-5") doesn't capture skill-specific performance. If the job required carpentry and painting, the auto-generated form includes: "Rate carpentry quality (1-5)", "Rate painting precision (1-5)" — which feeds directly into the Skill Gap Agent with granular data.

## Q8. How does the real-time chat system work in StreetGig?

**Answer:**

StreetGig uses **Firebase Realtime Database** for employer-worker chat rooms, not a dedicated messaging service.

### Data Model

```
jobs/
  rooms/
    {chatRoomId}/
      members/
        {userId}: { name, role, joinedAt }
      messages/
        {messageId}: {
          text: "Hello, when can you start?",
          senderId: "user_abc",
          senderName: "Ramesh",
          timestamp: 1711234567890,
          type: "text"
        }
      metadata/
        jobId: "job_xyz"
        status: "ACTIVE"
        createdAt: 1711234560000
```

### How It Works

1. **Room creation:** When a worker expresses interest in a job (or the employer contacts a recommended worker), a chat room is created under `jobs/rooms/{chatRoomId}`.

2. **Real-time sync:** Both parties attach RTDB listeners on `messages/` — any new message appears instantly (<100ms) on both devices.

3. **Component-level listeners:** Listeners are attached in `useEffect` with cleanup on unmount:
   ```javascript
   useEffect(() => {
       const messagesRef = ref(rtdb, `jobs/rooms/${roomId}/messages`);
       const unsubscribe = onChildAdded(messagesRef, (snapshot) => {
           setMessages(prev => [...prev, snapshot.val()]);
       });
       return () => off(messagesRef); // Cleanup on unmount
   }, [roomId]);
   ```

4. **Safety integration:** Users can report a chat room. The full transcript is sent to the Safety Agent for analysis.

**Why RTDB over WebSocket/Socket.io?**
- RTDB provides persistence, offline sync, and real-time updates out of the box
- No need to manage a WebSocket server
- Automatic reconnection on network changes
- Firebase Security Rules restrict access to room members only

## Q9. What is the Trajectory Agent and how does it track skill growth?

**Answer:**

The Trajectory Agent (`trajectory_agent.py`) tracks a worker's skill progression over time using **Exponentially Weighted Average (EWA)**.

### How EWA Works

Instead of simple averaging, EWA gives more weight to recent ratings:

```
EWA_new = α × latest_rating + (1 - α) × EWA_previous
```

Where `α` (alpha) = 0.3 (recency bias factor)

**Example — Worker's carpentry ratings over 5 jobs:**

| Job | Raw Rating | EWA (α=0.3) | Trend |
|---|---|---|---|
| Job 1 | 3.0 | 3.0 (initial) | — |
| Job 2 | 3.5 | 3.15 | Improving |
| Job 3 | 4.0 | 3.41 | Improving |
| Job 4 | 3.0 | 3.28 | Declining |
| Job 5 | 4.5 | 3.65 | Improving |

### Trend Detection

The agent classifies trends by comparing current EWA to the previous EWA:
- **Improving:** Current EWA > Previous EWA by > 0.2
- **Declining:** Current EWA < Previous EWA by > 0.2
- **Stable:** Within ±0.2 range

### Why EWA Over Simple Average?

Simple average treats all ratings equally. A worker who got 2/5 three years ago and 5/5 for the last 10 jobs would still have a dragged-down average. EWA naturally "forgets" old data, reflecting the worker's **current** competency level.

### Integration

The Trajectory Agent's output feeds into:
1. **Worker profile:** Displayed as skill trend badges (Improving/Stable/Declining)
2. **G-RAG scoring:** The reputation score component uses EWA, not raw average
3. **Scheme recommendations:** Declining skills trigger higher match scores against relevant training schemes

## Q10. How do Graph Writebacks work? What edges are created/updated in MongoDB?

**Answer:**

After every job completion, the system updates a knowledge graph in MongoDB's `graph_edges` collection. This graph is what G-RAG traverses during matching.

### Edge Types

| Edge Type | From → To | Created When | Purpose |
|---|---|---|---|
| `has_skill` | Worker → Skill | Profile creation, job completion | Maps worker capabilities |
| `skill_adjacency` | Skill → Skill | System seeding, LLM inference | Defines related skill clusters |
| `completed_for` | Worker → Employer | Job completion | Tracks employer-worker history |
| `skill_average` | Worker → Skill | Job rating received | Stores EWA rating per skill |
| `timeline` | Worker → Skill+Timestamp | Job completion | Chronological skill log |

### Writeback Flow After Job Completion

```python
async def update_graph(job_result):
    worker_id = job_result.worker_id
    employer_id = job_result.employer_id
    skills = job_result.extracted_skills   # From job enrichment
    ratings = job_result.ratings           # Quality, Punctuality, Comm

    # 1. Update has_skill edges (add new skills discovered from this job)
    for skill in skills:
        await upsert_edge("has_skill", worker_id, skill, {
            "confirmed": True,
            "last_used": datetime.now()
        })

    # 2. Update completed_for edge (employer-worker relationship)
    await upsert_edge("completed_for", worker_id, employer_id, {
        "job_count": increment(1),
        "last_rating": ratings.quality,
        "avg_rating": compute_ewa(existing_avg, ratings.quality, alpha=0.3)
    })

    # 3. Update skill_average edges (per-skill EWA ratings)
    for skill in skills:
        await upsert_edge("skill_average", worker_id, skill, {
            "ewa_score": compute_ewa(existing, ratings.quality, alpha=0.3),
            "total_jobs": increment(1)
        })

    # 4. Append timeline edge (immutable log)
    await insert_edge("timeline", worker_id, {
        "skill": skills,
        "rating": ratings,
        "timestamp": datetime.now(),
        "job_id": job_result.job_id
    })
```

### Why a Graph Instead of a Flat Database?

Flat queries like "find all workers with skill X" are fast, but they can't answer:
- "Find workers who have skills **adjacent to** X" (requires hop-1 traversal)
- "Find workers who have **worked for this employer before**" (requires relationship edges)
- "Find workers whose skills are **improving** over time" (requires timeline traversal)

The MongoDB graph approach (using `graph_edges` collection with `from`, `to`, `type` fields and a compound index) gives G-RAG the ability to answer these multi-hop queries without the overhead of a dedicated graph database like Neo4j.

## Q11. How does the fire-and-forget pattern work, and what are its failure modes?

**Answer:**

"Fire-and-forget" is used throughout StreetGig for non-critical AI processing:

```javascript
// In the Express controller
const jobId = await saveJobToDatabase(jobData); // Critical path
res.status(201).json({ jobId });                 // Respond immediately

// Fire-and-forget — don't await, don't block
axios.post(`${AGENT_URL}/process-job`, { jobId })
    .catch(err => console.error('Agent failed:', err));
```

### Why Fire-and-Forget?

1. **User experience:** The employer gets instant feedback (201 Created). AI enrichment takes 2-5 seconds — making them wait would feel sluggish, especially on slow networks.

2. **Fault isolation:** If the Python agent crashes, the job is still created and visible. The enriched embedding/skills will be missing, but the job is usable.

3. **Retry capability:** If the agent fails, the job exists in the database with `enriched: false`. A periodic cron job can pick up un-enriched jobs and retry.

### Failure Modes

| Failure | Impact | Mitigation |
|---|---|---|
| Python agent is down | Job created without embedding; won't appear in vector-based recommendations but IS visible in category/location browse | Background retry cron |
| Agent processes but embedding fails | Job has enriched text but no vector; partial enrichment | Agent retries embedding step 3 times internally |
| RTDB write fails (chat) | Message not persisted; sender sees it but receiver doesn't | RTDB has built-in retry; offline queue |
| Skill gap agent fails | Worker's gap vector not updated after this job | Next job completion will overwrite anyway |

### Consistency Trade-off

Fire-and-forget sacrifices **immediate consistency** for **availability and speed**. This is acceptable because:
- StreetGig's AI features are **enhancements**, not core functionality
- Jobs can be discovered by category/location without AI matching
- Workers can see and apply to jobs without embeddings
- The system is **eventually consistent** — enrichment happens within seconds
